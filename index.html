Enterprise REST API — Inventory Management

The Problem

Small warehouses were tracking inventory manually, leading to stock discrepancies and delayed reporting. Existing tools were either too expensive or lacked proper access control.

My Role

I designed and built the entire backend—database schema, REST endpoints, authentication, and deployment configuration.

Tech Stack
  • Java 17, Spring Boot 3, Spring Data JPA, Spring Security
  • MySQL with composite indexes and stored procedures
  • JWT-based authentication with role-based access control (Admin, Manager, Viewer)
  • JUnit + Mockito for unit and integration tests
Key Challenges
  • Concurrent stock updates: Two users updating the same item simultaneously caused race conditions. Solved using optimistic locking with versioning.
  • Slow queries: Report queries slowed down as data grew past 10K records. Added composite indexes and rewrote N+1 queries using JPA fetch joins.
  • Audit requirements: Every stock change needed to be traceable. Implemented an audit log table with triggers.
Outcome
  • API response time improved by approximately 40% after query optimization.
  • Successfully handled 10K+ records in test environments without performance degradation.
  • Role-based access eliminated unauthorized data changes.
What I Learned

This project taught me that database design decisions matter more than framework features. Most performance wins came from better queries and indexing, not from switching frameworks.

Microservices-Based E-Commerce Backend

The Problem

A monolithic e-commerce backend became difficult to scale and deploy. A single change required redeploying the entire application, and different modules had conflicting resource requirements.

My Role

I led the decomposition of the monolith into four microservices and set up the Docker-based deployment pipeline.

Tech Stack
  • Spring Boot, Spring Cloud (Eureka, Config Server, Gateway)
  • PostgreSQL per service (database-per-service pattern)
  • Docker + Docker Compose for local and staging environments
  • JWT propagation across services for stateless auth
  • GitHub Actions for CI/CD
Key Challenges
  • Inter-service communication: Order service needed catalog data. Solved using OpenFeign with fallback handling.
  • Distributed tracing: Debugging issues across services was hard. Added correlation IDs to all requests.
  • Configuration drift: Each service had its own config. Centralized using Spring Cloud Config.
Outcome
  • Each service could be deployed independently without affecting others.
  • Local development setup reduced to a single docker-compose up command.
  • Failures in one service (e.g., notifications) didn't cascade to order processing.
What I Learned

Microservices solve organizational problems more than technical ones. If you don't need independent deploys, a well-structured monolith is often the better choice.

Student Result Management System

The Problem

A local college managed student grades and reports using spreadsheets. Data was duplicated, report generation was manual, and there was no access control for teachers vs. administrators.

My Role

I built the desktop application end-to-end, including the database schema, UI, and report generation module.

Tech Stack
  • Core Java, JavaFX for the desktop UI
  • Hibernate ORM with MySQL
  • JasperReports for PDF report generation
  • Role-based access: Admin (full access), Teacher (grades only), Viewer (read-only)
Key Challenges
  • Transaction safety: Grade updates needed to be atomic. Used Hibernate transactions with proper rollback handling.
  • Report generation: Generating 500+ student reports took too long. Solved by batching queries and streaming PDF generation.
  • Data migration: Imported existing Excel data using Apache POI with validation rules.
Outcome
  • Handled 500+ student records with instant search and filtering.
  • Report generation time reduced from hours to minutes.
  • Eliminated duplicate data entry through centralized storage.
What I Learned

This was my first project where non-technical users were the primary audience. It taught me that UI clarity and error messages matter as much as backend correctness.

Task Automation Tool — CLI & Scheduler

The Problem

Routine data-processing tasks (CSV imports, report generation, email summaries) were being run manually, which led to missed deadlines and inconsistent results.

My Role

I designed and implemented the scheduling engine, retry logic, and notification system.

Tech Stack
  • Java, Spring Batch for job processing
  • Quartz Scheduler for cron-based job scheduling
  • MySQL for job metadata and execution history
  • JavaMail for failure alert emails
  • Maven for build management
Key Challenges
  • Failure recovery: A failed import should not leave partial data. Implemented chunk-based processing with rollback.
  • Retry logic: Transient failures (network issues) needed automatic retries with exponential backoff.
  • Idempotency: Re-running a job should not duplicate data. Added unique constraints and upsert logic.
Outcome
  • Routine tasks now run on schedule without manual intervention.
  • Failures trigger email alerts with error details.
  • Job execution history is logged for auditing.
What I Learned

Automation isn't just about scheduling—it's about failure handling. A job that works 99% of the time is useless if the 1% failure case corrupts data.

REST API Rate Limiter & API Gateway

The Problem

Downstream services were vulnerable to abuse and traffic spikes. There was no centralized way to enforce rate limits or log incoming requests across multiple services.

My Role

I built the gateway layer, implemented the rate-limiting algorithm, and configured route-based authentication.

Tech Stack
  • Spring Cloud Gateway for routing and filtering
  • Redis for token bucket state storage
  • JWT validation at the gateway level
  • Docker for containerized deployment
  • Custom filters for request logging and correlation IDs
Key Challenges
  • Distributed rate limiting: In-memory counters don't work across multiple gateway instances. Used Redis with atomic operations.
  • Fair throttling: Simple request-count limits punished legitimate bursts. Implemented token bucket with burst allowance.
  • Auth placement: Validating JWT at every service duplicated logic. Moved validation to the gateway and forwarded user context.
Outcome
  • Downstream services protected from abuse without code changes.
  • Centralized request logging simplified debugging.
  • Rate limits configurable per route without redeployment.
What I Learned

The gateway is the right place for cross-cutting concerns like auth, rate limiting, and logging. Pushing these into individual services creates duplication and inconsistency.
